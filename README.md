# 선착순 발급 아키텍처 비교 PoC

**"Redis 를 왜 쓰는가, 저장을 왜 비동기로 빼는가, 큐를 왜 내구 로그로 바꾸는가"**
를 태스트로 답하는 저장소입니다.

같은 기능을 4가지 아키텍처로 만들고, **같은 조건에서 나란히 재서** 각 선택의 근거를 수치로 만들었습니다.

---

## 결론 먼저

목표 시나리오: **재고 10,000장 / 동시 20,000명 / 초과 발급 0건**

| | v0 MySQL 락 | v1 + Redis 판정 | v2 + 비동기 저장 | v3 + 내구 로그 |
|---|---|---|---|---|
| **응답 p99** | 14,203ms | 4,506ms | **1,101ms** | **846ms** |
| **에러율**(15초 초과) | **50%** | 0% | 0% | 0% |
| 커넥션 풀 대기 | 191 | 190 | **0** | **0** |
| 프로세스 강제 종료 시 | - | - | **전량 유실** | **유실 0** |
| 초과 발급 | 0 | 0 | 0 | 0 |

```
p99   14,203ms  →  4,506ms  →  1,101ms      누적 12.9배
```

세 번의 아키텍처 변경이 각각 무엇을 해결했는지가 이 문서의 내용입니다.

### 그래서 우리는 이렇게 만듭니다

위 표를 읽는 방법은 이렇습니다. **v0 는 쓸 수 없고, v1 은 느리고, v2 는 유실되고, v3 만 남습니다.**

| 계층 | 채택 | 근거가 된 수치 |
|---|---|---|
| **판정** | Redis Lua 원자 실행 | v0 는 20,000 에서 **에러율 50~84%**, v1 은 **0%**. 락 하나가 처리량 상한을 만든다 |
| **저장** | 비동기 + 배치 500 | 커넥션 풀 대기 **190 -> 0**, p99 **4.1배**. pool 을 5배 늘려도 비동기의 3배 뒤 |
| **큐** | Redis Stream Outbox<br>(`XADD` 를 Lua 안에) | 메모리 큐는 프로세스 종료 시 **전량 유실**, Stream 은 **0**. 게다가 v3 가 더 빠르다 |
| **영속화** | **Redis AOF 를 켠다** | 끄면 브로커가 죽을 때 **10,000건 전량 유실**. v3 의 "유실 0" 은 AOF 가 켜져 있을 때만 |
| **앱 대수** | 2대 이상 | CPU 가 분리되면 **45% 개선**. 단 **커넥션만 늘리면 오히려 나빠진다**(에러 6% -> 24%) |
| **DB pool** | 10 유지 | 늘려도 대기가 사라지지 않는다. `poolPending = 톰캣 스레드 - pool` |
| **앱 사양** | **4 vCPU 이상** | 2 vCPU 는 20,000 을 겨우 소화. CPU 가 먼저 막히면 아키텍처를 바꿔도 차이가 사라진다 |

**Kafka 는 내구성 때문에 쓰는 게 아닙니다.** 브로커 장애 대비는 Redis AOF 만으로 유실 0 이 됐습니다.
Kafka 가 추가로 주는 것은 **다중 컨슈머 팬아웃 / 장기 리텐션 / 노드 복제**이고,
그건 이 측정이 답할 수 있는 영역이 아니라 **요구사항 판단**입니다.
쓸 이유가 있다면 그 이유로 쓰고, 없다면 Stream 으로 충분합니다.

> **결론만 필요하면 여기까지입니다.** 아래는 각 선택의 근거와 반례를 검증한 기록입니다.

## 1. 왜 이 테스트가 필요한가

매일 정오에 쿠폰 10,000장이 풀리고, **그 1초에 20,000명이 몰립니다.**
요구는 하나입니다 -> **초과 발급 0건, 1인 1매.**

Redis 로 판정하고 Kafka 로 저장을 흘리는 구조가 정석이라고들 하지만,
정석이라서 설계? -> 근거 X -> 그래서 다음을 직접 만들어 비교했습니다.

| | 판정 | 저장 | 큐 |
|---|---|---|---|
| **v0** | MySQL `SELECT ... FOR UPDATE` | 동기 | - |
| **v1** | Redis Lua (원자) | 동기 | - |
| **v2** | Redis Lua | 비동기 배치 500 | JVM 메모리 |
| **v3** | Redis Lua + `XADD` | 비동기 배치 500 | Redis Stream (Outbox) |

**한 단계에 변수 하나만 바꿉니다.**

## 2. 테스트 환경

두 환경에서 쟀습니다. **로컬은 상대 비교용, AWS 는 그 비교가 환경 탓이 아님을 확인하는 용도입니다.**

| | 로컬                           | AWS (`ap-northeast-2`, 같은 AZ)         |
|---|------------------------------|---------------------------------------|
| 구성 | 앱,MySQL,Redis,k6 **한 대에 전부** | db / app1 / app2 / load **4대 분리**     |
| 사양 | 10코어 / 16GB                  | c5.large(2vCPU) ×3 + c5.xlarge(4vCPU) |
| 한계 | CPU 를 나눠 써 **절대치를 믿을 수 없다**  | 앱이 2코어라 **로컬보다 절대치가 낮다**              |
| 비용 | 0원                           | 30분 **340원**(아직 0원)                   |

- 부하 도구 **k6** (`load/issue.js`). `per-vu-iterations` 로 전 VU 를 t=0 에 동시 발사 -> 정오 정각 스파이크 재현
- 응답시간은 **`http_req_waiting`(TTFB, 서버가 일한 시간)** 을 씁니다. `http_req_duration` 은 클라이언트 사정이 섞입니다

### 통제 변수 (전 측정 고정)

```yaml
hikari.maximum-pool-size: 10     # pool 민감도 실험만 예외(50)
hikari.connection-timeout: 10s   # 실패 원인을 귀속시키려 명시
tomcat.threads.max: 200
tomcat.accept-count: 20000       # 기본 100 이면 TCP 백로그에서 대기해 측정에 안 잡힌다
tomcat.max-connections: 20000    # 기본 8192. 20,000 부하에서 딱 8,192건만 응답이 온 원인
k6 timeout: 15s                  # pool 대기 10s < 15s 라야 서버 실패가 서버 숫자로 잡힌다
재고: 10,000 고정                 # 부하만 바꾼다
```

부하 생성기가 먼저 무너지면 p99 가 오히려 좋아 보입니다(coordinated omission).
그래서 실험 전에 도구의 한계부터 측정했습니다 = k6 는 20,000 까지 버팁니다.

## 3. 시나리오와 근거 - 순서대로

### ① Redis 판정 도입 근거 (v0 → v1)

저장 방식을 고정하고 **판정만** MySQL 락에서 Redis Lua 로 옮겼습니다.

| 동시 20,000 | v0 | v1 |
|---|---|---|
| **에러율** | **50%** (로컬) / **84%** (AWS) | **0%** |
| **거절(409) 응답** | **0건** | 10,000건 정상 |
| 응답 p99 | 14,203ms | 4,506ms |
| 저장 처리율 | 545/s | 1,204/s |

> **v0 는 절반 이상이 15초 안에 응답을 못 받습니다.**
> "재고 없습니다" 라는 거절조차 돌아오지 않았습니다.

원인은 **`stock` 단일 row 를 잠그기 때문**입니다. 처리량 상한이 `1 / 락 보유시간` 으로 고정되어
부하를 10배 올려도 TPS 가 오르지 않습니다(1,455 → 1,305 → 1,082).

**저부하에서는 거절 비용으로도 보입니다**
v0 는 거절 p99(654ms)가 성공(544ms)보다 **비쌉니다.**
거절 한 건에도 커넥션을 잡고 락을 기다리기 때문입니다. 
v1 은 Redis 에서 끝나고 DB 를 건드리지 않습니다.

### ② 비동기 저장 도입 근거 (v1 → v2)

판정을 고정하고 **저장만** 동기에서 비동기 배치로 바꿨습니다.

| 동시 20,000 | v1 | v2 |
|---|---|---|
| 응답 p99 | 4,506ms | **1,101ms** (4.1배) |
| 저장 처리율 | 1,204/s | **2,019/s** |
| **커넥션 풀 대기** | **190** | **0** |
| 저장 적체 흡수 | - | **최대 4,296건** |

**`poolPending` 190 → 0 이 병목 위치의 직접 증거입니다.**
190 은 톰캣 스레드 200개 중 190개가 커넥션을 기다리며 묶여 있다는 뜻입니다.

**그럼 커넥션 풀만 늘리면 되지 않나?** -> 재봤습니다.

| v1 | pool 10 | pool 50 |
|---|---|---|
| 20,000 p99 | 3,898ms | 3,142ms (1.2배) |
| `poolPending` | **190** | **150** |

```
poolPending = 톰캣 스레드 200 - pool 크기
```

**pool 을 늘리는 것은 대기하는 스레드 수를 줄이는 것이지 대기를 없애는 게 아닙니다.** 
0 으로 만들려면 pool 을 200 으로 = MySQL 에 동시 커넥션 200개입니다.
5배 늘려도 고부하 개선은 20%, 비동기의 **3배 뒤**에 머물렀습니다.

### ③ 내구 로그(Outbox) 도입 근거 (v2 → v3)

비동기를 유지하고 **큐만** JVM 메모리에서 Redis Stream 으로 바꿨습니다.

v2 의 문제는 응답 직후 상태에서 드러납니다.

```
응답 직후:  dbIssued 0   queueSize 10,000   redisIssuedBits 10,000
            ↑ Redis 는 발급됐다는데 DB 에는 없다. 이 창에서 죽으면?
```

| 프로세스 `kill -9` 후 재기동 | v2 | v3 |
|---|---|---|
| 결과 | **10,000건 전량 유실** | **유실 0** |

핵심은 `XADD` 를 **Lua 안에** 넣은 것입니다. 판정, 차감, 이벤트 발행이 한 덩어리(원자)라
서버가 죽어도 이벤트가 Redis 에 남습니다 (Transactional Outbox).
v2 는 판정(Redis)과 큐 적재(JVM)가 다른 곳에 있어 그 틈에 죽으면 재고만 줄고 이벤트가 사라집니다.

**소비자만 멈춰도 복구됩니다** - relay 정지 후 부하 → 재개하면 **171ms 에 10,000건 수렴.**

**그럼 대가는?** 없었습니다.

| 동시 20,000 (3회 중앙값) | v2 | v3 |
|---|---|---|
| 응답 p99 | 1,101ms | **846ms** |
| GC 비율 | 8.40% | **7.63%** |

v3 가 오히려 빠릅니다. v2 는 최대 4,296건을 **JVM 힙에** 들고 있고, v3 는 Redis 에 있어
힙 부담이 밖으로 나갑니다. **내구 로그는 유실만 막는 게 아니라 메모리 압박도 줄입니다.**

#### 브로커도 죽습니다 - 영속화가 필요합니다

Redis 자체를 `kill -9` 했습니다.

| Redis AOF | 유실 |
|---|---|
| `off` (인메모리) | **10,000건 전량** |
| `everysec` / `always` | **0** |

> **v3 의 "유실 0" 은 앱 장애 한정입니다.** 브로커 장애까지 막으려면 AOF 가 켜져 있어야 합니다.

### ④ 수평 확장으로는 풀리지 않습니다

모체는 이미 앱을 2대로 운영합니다. 그래서 **앱을 늘리면 되는지** 쟀습니다.
총 DB 커넥션을 20 으로 맞춰 **앱 대수만** 다르게.

| v1 × 20,000 (AWS) | N1 1대/pool10 | N1-20 1대/pool20 | **N2 2대/각10** |
|---|---|---|---|
| 에러율 | 6% | **24%** | **0%** |
| 응답 p99 | 11,515ms | 12,537ms | **6,902ms** |
| 저장 처리율 | 443/s | 430/s | **611/s** |

앱 확장은 효과가 있습니다(45% 개선). 하지만 **커넥션만 늘리면 오히려 나빠집니다**(에러 6% → 24%).
그리고 확장으로도 v2 의 1,101ms 수준에는 닿지 못합니다.

> **확장은 붕괴를 완화하지만 성능을 회복하지 못합니다.**
> 응답을 받게 되는 것과 빠르게 받는 것은 다릅니다.

### ⑤ 정확성은 전 구간에서 지켜졌습니다

**전 회차/전 부하/양 환경에서 초과 발급 0건.** `dbIssued` 가 재고를 넘은 적이 없습니다.

1인 1매도 따로 검증했습니다 - 1,000 VU 가 userId 100개를 공유 →
**발급 100건 / 중복 거절 900건 / `dbIssued` 100**

빠른데 틀리면 의미가 없으므로 이 항목이 실패하면 성능 수치는 전부 무효로 봅니다.

## 4. 예상과 달랐던 것

측정하면서 예상이 깨진 지점들입니다.

| # | 예상 | 실제 |
|---|---|---|
| 1 | 거절 비용(409 p99)이 Redis 근거 | **20,000 에서 v0 는 409 가 0건.** 지표가 사라져 **에러율**로 교체 |
| 2 | 무한 큐가 GC 를 악화시킨다 | **큐 없는 v0 도 heap 891MB.** 큐 탓이 아님 → 바운드 큐 근거 없음 |
| 3 | `XADD` 가 늘었으니 v3 가 느리다 | **v3 가 23% 빠름.** 힙 부담이 Redis 로 나가서 |
| 4 | 부하를 올리면 처리량이 오른다 | **10,000 에서 정점, 20,000 에서 감소.** 경합이 처리량을 깎는다 |
| 5 | 앱을 늘려도 소용없다 (로컬 결론) | **AWS 에서 뒤집힘.** 앱 2대가 같은 CPU 를 나눠 쓴 탓이었다 |
| 6 | fsync 를 켜면 성능 대가가 있다 | **측정 불가.** `docker kill` 은 페이지 캐시를 남긴다 |

**5번이 가장 큽니다.** 로컬에서 앱 프로세스를 2개 띄웠지만 같은 10코어를 나눠 썼으므로
실제로는 확장이 아니었습니다. AWS 에서 CPU 를 분리하니 결론이 뒤집혔습니다.

같은 종류로, **관측 도구가 결론을 반대로 만든 사례**도 있었습니다 -
`/stat` 폴러가 부하와 톰캣 스레드를 경쟁해 `poolPending` 피크를 놓쳤고,
그래서 한동안 "pool 은 병목이 아니다" 라는 반대 결론을 들고 있었습니다.
폴러를 전용 커넥터(8081)로 분리하니 190 이 안정적으로 관측됐습니다.

## 5. 이 테스트가 답하지 못하는 것

| 질문 | 이유 |
|---|---|
| "초당 몇 건 처리하나" | 닫힌 부하 모델이라 TPS 가 종속 변수입니다. "2만명이 다 끝나는 데 걸린 시간의 역수" 로 읽어야 합니다 |
| "동시 20,000 을 처리했나" | 아닙니다. 서버가 겪은 동시성은 **항상 200**(톰캣 스레드). 20,000이 큐에 쌓였다가 200씩 빠진 것입니다 |
| **"v1 은 몇 명에서 무너지나"** | AWS 2vCPU 에서 **CPU 가 먼저 병목**이라 30,000/40,000 에서 v1/v2/v3 에러율이 전부 같았습니다. 4~8 vCPU 로 재측정해야 합니다 |
| "Redis Stream 말고 Kafka 여야 하는 이유" | 브로커 내구성은 **AOF 만으로 확보**됐습니다. Kafka 의 추가 가치(팬아웃/리텐션/복제)는 측정 대상이 아니라 **요구사항 판단**입니다 |
| 누적 데이터 영향 | `issue` 를 매 회차 `TRUNCATE` 해 **인덱스가 항상 최적 상태**였습니다. 실제 서비스는 누적되므로 절대치는 낙관적입니다(격차는 더 벌어질 방향) |

**병목은 사양에 따라 이동합니다.** 로컬 10코어에서는 저장 계층이, AWS 2코어에서는 CPU 가 병목이었습니다.
→ 아키텍처를 바꾸기 전에 **사양이 맞는지** 먼저 봐야 합니다.

## 6. 재현 방법

```bash
# 1. 인프라 (MySQL 3308 / Redis 6380 - 다른 프로젝트와 충돌 회피)
docker compose up -d

# 2. 앱
./scripts/app.sh start            # bootJar → java -jar, 8080 / 폴러 8081

# 3. 계약 확인
curl -X POST localhost:8081/reset
for v in v0 v1 v2 v3; do
  curl -s -o /dev/null -w "$v %{http_code}\n" -X POST "localhost:8080/$v/issue?userId=1"
done                              # 기대: v0 200 / v1 409 / v2 409 / v3 409

# 4. 탐색 측정 1회 (버리는 숫자)
./scripts/probe.sh v1 1000

# 5. 본 측정 17회차 (~25분)
./scripts/run.sh

# 6. 장애/확장 실험
./scripts/run-pool.sh             # pool 10 vs 50
./scripts/broker-kill-test.sh     # Redis AOF 3모드 × 브로커 kill
./scripts/run-scale.sh            # 앱 1대 vs 2대

# 7. 표/그래프
python3 scripts/parse.py          # → docs/results/
```

**k6 가 필요합니다**(`brew install k6`). 
리눅스/macOS 커널 튜닝이 선행돼야 20,000 이 가능합니다 -
macOS 는 임시 포트가 16,384 뿐이라 20,000 동시 연결이 **물리적으로 불가능**합니다.

```bash
sudo sysctl -w net.inet.ip_local_port_range... # macOS: portrange.first=10000
sudo sysctl -w kern.ipc.somaxconn=20000
sudo sysctl -w net.inet.tcp.msl=1000
```

## 8. 측정 설계에서 배운 것

| | |
|---|---|
| **관측이 대상을 흔든다** | 폴러가 부하와 스레드를 경쟁해 결론이 반대로 나왔습니다. prometheus 스크레이프를 200ms 마다 하는 것도 같은 이유로 뺐습니다 |
| **통제하지 않은 변수가 먼저 무너진다** | `max-connections`(8192), `accept-count`(100), `somaxconn`(128), 임시 포트(16,384) - 전부 측정 대상보다 먼저 한계에 닿았습니다 |
| **에러 없이 틀리는 버그가 가장 위험하다** | 드레인 수렴 조건, GC 변수 섀도잉, 적체 지표 - 전부 그럴싸한 숫자를 내놓았습니다 |
| **차이 크기에 따라 방법이 달라야 한다** | 3배 차이는 1회로 판별되지만 수십 % 차이는 3회 중앙값이 필요합니다 |

> v0 은 MySQL row 에, v1~v3 은 Redis 카운터에 두었습니다. 그 차이가 p99 13~28배입니다.
